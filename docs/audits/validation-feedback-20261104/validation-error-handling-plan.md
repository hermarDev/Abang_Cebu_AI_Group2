# Validation and feedback implementation roadmap

This is a proposal, not implementation approval. Source and scope: [audit](validation-feedback-audit.md); wording: [inventory](error-message-inventory.md); UI choices: [component matrix](feedback-component-matrix.md); library choices: [architecture](ui-library-architecture-audit.md); tests: [test matrix](validation-e2e-test-matrix.md). Snapshot includes uncommitted and untracked work; do not commit it wholesale or assume ownership.

## Gates

1. User separately approves implementation and any dependency changes. Reinspect HEAD, dirty/staged/untracked files, worktrees, exact coordination rows, and inherited ownership. Acquire atomic claims for exact paths before writes; do not modify another owner's claimed paths. A read-only audit claim is not permission to write source. No release, push, live provider or DB changes without separate applicable authorization.
2. Before each code task, write a targeted regression and demonstrate intended behavior fails; distinguish harness/setup failure from behavioral RED. Implement the minimum; rerun that same check and nearby tests, then browser proof where authorized. Record exact command, exit code and source snapshot. Test-only green or toast text is not proof of persistence.
3. One writer per overlapping file set. Freeze response contract before frontend/backend parallelism; handoffs must identify exact source, test and claim ownership. Independent QA and Security assess stable result, not partial code. Record reviewer outcomes and unresolved hypotheses.

## Practical execution loop

For each approved task: (1) inspect live code and tests; (2) claim all exact files atomically; (3) add one focused failing regression; (4) run `pnpm exec vitest run <actual-test-path>` and retain the intended assertion failure; (5) implement minimal fix; (6) rerun focused unit and relevant mounted browser checks; (7) run `pnpm run lint`, `pnpm exec tsc --noEmit --incremental false`, `pnpm run test`, and `pnpm run build` as applicable, with separate exit statuses and safe isolated server; (8) independent review; (9) inspect diff and hand off. These commands are future proposals, not tests executed during this audit. Before any commit, publication or Git changes obtain the required explicit authorization and ensure no unrelated inherited change is staged.

## Decision points

- Accept source-confirmed VF-01–VF-05 and choose which tasks to implement.
- Authorize isolated browser tests and, separately, disposable Supabase/auth/storage infrastructure if desired.
- Decide current password policy only after assessing provider and security requirements. Reject arbitrary weakening of server validation.
- Add Sonner, React Hook Form, Zod or TanStack Query only if a specific evidence-backed benefit outweighs duplicate implementations and peer/migration costs. No package upgrade is implied by this plan.

## Ownership and deliverable limitations

Static findings from this audit are grounded in local source, not production execution. Report any inaccessible environment, active claim, failed review or missing test as BLOCKED/NOT RUN. The audit does not authorize code, tests, data, Git, deployment or hosted settings mutations.
